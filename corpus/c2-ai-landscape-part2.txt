Take one response from an LLM inside our application — for example, the answer to a support ticket.
Before you can actually use it, act on it and eventually pass it along to a user, you must evaluate how correct
the response is.
But "Is this response correct?" is really several questions at once:
Dimension Question we ask about the LLM's response
Syntax Can our application parse it?
Schema Does it have the required fields and types?
Semantics Does it mean the right thing?
Factuality Are the claims it makes supported by real facts or sources?
Safety Is the content (or the action it triggers) acceptable?
Business correctness Does it satisfy the product requirement?
A response can pass the first two rows and fail all the others.
A valid structured output (JSON) is not the same thing as a correct answer.

The same input can produce a diﬀerent output on two separate calls, even with identical parameters.
It comes from sampling: the model picks probabilistically among likely next tokens. This is a property, not a
bug.
temperature controls how much randomness. Setting it to 0 reduces variation but does not fully
guarantee identical outputs across calls (Session 2 explains why).
Therefore:
You cannot write a traditional unit test asserting output === "exact string"
You need repeated evaluation and explicit acceptance criteria.
Some nuance: non-determinism is not necessarily a defect. Creative generation may require variation. The
engineering problem is knowing when variation is acceptable.

The model proposes; the application decides.
Definition: Least privilege means every user, service or agent gets only the permissions its current task requires,
for only as long as it needs them. If it is compromised, fooled or simply wrong, the damage is limited to what it
was allowed to do.
Why AI makes this urgent: a model is steered by text, including text from attackers (prompt injection, poisoned
documents). Its "intentions" cannot be treated as a security property, so its access has to be limited.
