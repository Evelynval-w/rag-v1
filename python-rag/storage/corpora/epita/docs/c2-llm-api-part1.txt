A model writes its answer one token at a time. At each step it computes a probability for every possible next token, then
one token is picked.
Temperature reshapes these probabilities. Higher = more adventurous choices; lower = more predictable choices.
At temperature 0, the most probable token is always picked ("greedy" choice).
Every following token depends on the tokens before it, so one diﬀerent early choice changes everything after it.
Top-k and top-p also narrow the choice: top-k only picks among the K most probable tokens; top-p only picks among
the smallest set of tokens whose probabilities add up to p.

But if temperature is 0, there is no randomness in the picking. So why do answers still diﬀer?
Because the probabilities themselves can change slightly from one call to the next:
The provider's servers are shared. Many requests are processed together in batches, and the batch that contains your
request depends on whoever else is calling at that moment.
Depending on the batch, the GPU splits and orders its arithmetic diﬀerently. And in floating-point arithmetic, the
order of operations changes the result:
Try it yourself: 
The diﬀerences are tiny — normally invisible. But when two tokens are almost tied (say 50.1 % vs 49.9 %), a tiny
diﬀerence can flip the winner, and the rest of the answer follows a diﬀerent path.
Temperature 0 makes variation rarer. It does not make it impossible.

In real deployments there are more moving parts:
Model aliases move. A name like ...-latest can point to a new version next month.
Gateways and routers: requests routed to diﬀerent hardware replicas behind a load balancer.
Fallbacks. If you configure a second (or third) model for when the first one is unavailable, your results now come from
models with diﬀerent styles, strengths and failure modes. The type and quality of results can fluctuate a lot: a fallback
keeps the feature available, not necessarily equally good.
