A prompt is closer to a function signature than to a chat message. It runs over and over with
diﬀerent data, and nobody reads each answer before the application uses it.
Two roles:
system: you, the engineer, wrote it: the rules that stay the same for every request.
user: the input: the ticket, wrapped in <ticket>…</ticket>.

Not every prompt needs every part. Use the list to notice what you forgot to say:
1. Role / context: who the component is
2. Task: what to do with the input
3. Allowed values / constraints: the four categories, the three priorities
4. Decision guidance: business rules. For example: "priority reflects business impact, not tone"; "how-to
questions are filed as technical_bug / low"
5. Examples: optional, see the next slide
6. Input data: the ticket, in <ticket> tags
7. Output requirements: what the answer must contain

[page 18]
Few-shot = show a few solved examples (input → expected output) before the real input. It was
essential with older models. With recent models, try zero-shot first: examples mainly help with
judgment at the boundaries, and smaller or cheaper models often need them more. Measure: run the
tickets with and without.
Chain-of-thought = ask the model to reason step by step before answering. Many models reason
internally now, and that reasoning is billed as output. For triage we want reliable decisions and
testable outputs, not a transcript. If a human needs an explanation, add an explicit rationale
field to the schema, rather than relying on hidden reasoning text.

user.

suggested action.
User message: the ticket inside <ticket> tags. The ticket text is subject + "\n\n" +
body.
