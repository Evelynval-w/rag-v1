A vector database stores chunks and finds the nearest ones to a query vector.
For each chunk it stores:
the vector (computed by your embedding model)
the text (what you will send to the LLM)
the metadata (source file, position, date, access rules etc...)
It provides two operations:
add: store a chunk's vector, text and metadata during indexing
query: given a query vector, return the top-k most similar chunks, optionally filtered by metadata
Examples:
ChromaDB: local, runs in your application, used in our lab
Pinecone: managed cloud service

[page 39]
You choose an embedding model, separately from the chat model.
You cannot reuse the llm model's internal states as a search index. Those states are the activations the
transformer computes while it reads a prompt: one vector per token, per layer. They depend on the surrounding
text, were not trained for retrieval, and hosted APIs do not expose them.
Queries and chunks must be embedded with the same embedding model.
Changing the embedding model means re-indexing everything: the spaces are not comparable.
Keep in mind: A similarity score is not a confidence: 0.83 does not mean "83 % correct".
