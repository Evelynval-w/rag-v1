An LLM API lets your code talk to a pretrained model, hosted remotely (or locally), over HTTP.
You send a prompt, and often a conversation history.
You get generated text back — usually streamed token by token.
Some things worth knowing right away:
Examples: Anthropic's Claude, OpenAI's GPT models, Google's Gemini, and open-weight
models served through aggregators such as OpenRouter, Hugging Face or OpenCode
Usage is typically priced per token, for input and output, usually at diﬀerent rates — do you
know why?
The API is stateless by default: it does not remember previous calls, so you resend the
context every time
What you will actually touch in Session 2:
authentication (API keys, environment variables — never in client code!)
request structure: system prompt, message history, parameters (temperature, max tokens)
streaming vs. blocking responses
rate limits and provider error codes

An LLM's knowledge comes entirely from training: a large, fixed snapshot of text, frozen at a
knowledge cutoﬀ. Once training ends, the weights don't change.
That leaves two permanent gaps:
Recency Gap — this morning's inventory, this week's incident, a policy that changed last
month
Access Gap — your company's internal documents, a specific user's account or history,
records that were never public
Most real AI features — as opposed to a general chatbot demo — live squarely inside one of
these gaps: "summarize this user's tickets", "answer from our internal policy", "check today's
stock level".
This isn't a bug to patch. It is a permanent property of any trained model.

"WHY NOT JUST RETRAIN THE MODEL ON OUR DATA?"
Fair question.
Fine-tuning is one real path, but:
it is expensive and slow — data curation, training runs, GPU cost (that is the ML-engineering
column from earlier, not the one this course lives in)
it has to be redone whenever the data changes
it is opaque — harder to inspect why the model produced a given answer
The alternative this course focuses on: leave the weights untouched and supply the missing
information fresh, at request time, in the context window.
But your data is almost always far bigger than any context window, and stuﬀing all of it into
every request runs straight into the cost and latency problems we discuss in Part II. So the real
engineering question becomes:

A piece of text (or an image, audio, etc.) converted into a vector — a fixed-length list of
numbers — such that:
semantically similar content produces nearby vectors
Concretely: "cat" → [0.12, -0.04, 0.91, ..., 0.33]
An embedding is a coordinate, not an answer. It means nothing on its own; what matters is
how it compares with another embedding. In practice that comparison is usually cosine
similarity: the angle between two vectors, not the raw distance between them.

The naive way to turn a token into a vector is one-hot encoding: a vector as long as the entire
vocabulary, all zeros except a single 1.
It is sparse, huge and — critically — says nothing about meaning: "cat" and "kitten" are
exactly as far apart as "cat" and "refrigerator".
An embedding replaces that with a small, dense vector that does encode meaning:
Embedding model Typical dimension
Lightweight / cost-optimized models 256–512
BERT-base, many open models 768
OpenAI text-embedding-3-small 1,536
OpenAI text-embedding-3-large 3,072
That is an embedding space one or two orders of magnitude smaller than the vocabulary —
roughly 30× to 100× fewer dimensions.
The point: take a huge, meaning-blind list of IDs and squeeze it into a much smaller space
where distance finally means something.

So far we have talked about embedding a token. But we also need to "embed" whole
sentences, paragraphs and documents.
How do we get from one token embedding to a variable length text?
Text Tokens

one contextual

The embedding model first produces a vector per token, and each one already takes the
surrounding words into account (so "bank" in river bank and bank account diﬀer).
A pooling step (for example averaging, or using a special summary token) collapses them
into one fixed-length vector for the whole text.
These embedding models are trained so that texts with similar meaning end up with similar
vectors.
Whatever the length of the text, you get the same number of dimensions back — which is
what makes comparing and searching them possible.

A vector database is optimized to store embeddings and answer the question "what is most
similar to this vector?" at scale, instead of exact-match queries.
Examples: ChromaDB, Pinecone (managed), Weaviate (managed or self-hosted), pgvector
(an extension that adds vector search to plain PostgreSQL)
Under the hood: approximate nearest-neighbour (ANN) search, which trades a little
accuracy for large speed gains
In AI Systems, their role is to help Retrieve the most similar chunks of text that will be
relevant to the current prompt.

Agent frameworks are libraries that orchestrate multiple LLM calls, tool use and state into a
workflow, instead of a single prompt → single response.
Examples: LangChain, LlamaIndex, CrewAI, Google ADK (Agent Development Kit)
Typical pattern: the LLM decides which tool to call (search the web, query a database, run
code), observes the result, and decides the next step — which may involve more LLM calls
Powerful, but it adds failure surface: more calls, more places for cost and latency to spiral,
more places for the chain to go wrong.
Worth asking yourself: "What new failure modes appear once the model can take actions?":
wrong tool, repeated loops, unintended side eﬀects, permissions, costs, tool failure, prompt
injection through tool results.
