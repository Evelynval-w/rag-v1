"decision model" is the generic term.
TypeSafe, who introduced the category with their decision model named Jev, calls them "System One" models (after
Kahneman's fast, intuitive "System 1" thinking).
Daniel Kahneman, a Nobel Prize-winning psychologist, modeled "System 1" as the brain's fast, involuntary, and intuitive
shortcut engine.

A decision model takes a state and typed questions about it. It answers each question with a probability, not a
sentence.
state: the thing to judge: a text, a web page, an agent trace
questions: what must be decided, each with a fixed answer format
Three types of questions:
Type Question Answer
choice pick one option among a closed set the chosen option, plus a probability per option
noul a yes/no question a probability between 0 and 1
score rate on an ordered scale a score, plus a probability per level

Key idea: a decision model cannot answer outside the options you gave it, and it tells
you how sure it is.

Decision models are not:
the next version of LLMs
a replacement for LLMs
able to write, summarize, explain, plan or reason in several steps
Think of a decision model as an intelligent switch statement: you give it a situation and the options, it picks one,
with a probability.
It is one more tool in the toolbox. Everything you learned in Parts I and II about LLMs remains true. The question is
whether one specific part of your feature is better served by a diﬀerent tool.

An LLM writes token by token: one pass through the whole network for every token it produces. A decision model reads
the input once, and scores the allowed answers:
Most are built on top of an existing model, with the text-generation part replaced by a scoring part:
Model Maker Built on Size
Clef / Clef-flash Cloudflare Qwen3.8 / Qwen3.5, frozen, plus small trained adapters and a scoring head 27B / 9B
Strands Decider AWS a small LLM plus a scoring head of about 1 million parameters 1.9B
Laya open source an encoder model (ModernBERT), not an LLM 421M
Decisions API OpenAI "a version of" GPT-6 Luna not disclosed
Jev TypeSafe not disclosed not disclosed
Not necessarily small. Clef is a 27-billion-parameter model.
Training goes beyond "get the right answer": it rewards calibrated probabilities. When the model says 0.9, it should be
right about 9 times out of 10.
Key Idea: Read once, answer many questions in one pass.

[page 8]
Not because they are smaller. Because of how they work:
1. No generation loop. An LLM producing a 150-token JSON runs 150 sequential steps. A decision model runs one.
2. No output tokens. Providers typically bill the input only: the answer is a few numbers.
3. Questions are answered in parallel. Adding a question barely changes the response time.
4. Always the right shape. No code fence, no missing key, no invented value, no retry for invalid output: the problems of
Part I sections 5 and 6 do not exist.

The category is weeks old. What the early independent tests say:
Confidence is not always honest. One test on a 77-case banking set: 87% average confidence, 75% actual accuracy.
Another tester got an 80% confidence on a fair die roll.
Agreement is not correctness. One study found a decision model agreed with a frontier LLM 6 to 8 points more often
than it matched the ground-truth labels.
Many labels hurt. Accuracy drops on large label sets. Our label sets are small: that is in our favour.
Typed output constrains the shape, not the judgment. A clean answer with a high confidence can still be wrong,
especially between two close options ( breakfast or snack?).
Vendor numbers are vendor numbers.

F1: Structured triage flow with JSON schema and Zod validation
The triage request and the triage response each follow a JSON schema.
Payloads are validated with Zod against that schema before they are forwarded to the user.
Invalid requests show a clear error on the front end instead of failing silently. F2: Token usage display
Each triage result on the front end shows the token usage of its LLM call (input, output and total tokens). F3: Smoke
test runner
The smoke test is started from the front end.
The user chooses the dataset (the labelled 100-ticket set or the 500-ticket set) and how many tickets to sample at
random from it.
Results are displayed on the front end.
For the labelled 100 set, each ticket shows the category and priority predicted by the LLM next to the category and
priority from the labelled set.
For the labelled 100 set, a summary at the end shows how many predictions are mismatched, for category and for
priority. F4: Smoke test logging and admin page
Each smoke test run is logged with its accuracy, outcome counts, latency, cost and the name of the LLM model used.
An /admin page lists every logged run with these values. F5 (optional): Model switching and comparison
The front end has a menu to switch the LLM model. This requires access to more than one model.
The user can re-run the smoke test with another model, and the /admin page shows the two runs side by side for
comparison.
